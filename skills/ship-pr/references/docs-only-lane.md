# Docs-only lane

This is ship-pr §1.5. Section numbers (§0–§7) refer to [`../SKILL.md`](../SKILL.md).

Two entry gates, both hard. Evaluate them on the PR head against its base
(`git diff <base>...HEAD` after the §1 commit; take `<base>` from the latest §0 pin's
`BASE_OID`, or from the base's remote-tracking ref after a fetch where no pin ran,
because a local base branch can be behind its remote), never on this run's increment, and
re-evaluate them every time that diff changes — a §5 merge with a collaborator, a §6 fix,
a re-run on a branch that already carries code. A diff that leaves the lane runs §2 and
§3 in full, and its PR body is corrected to match before you claim anything.

1. Every file in that diff is a `.md` file. One non-`.md` file — a workflow, a script, a
   config, a fixture — sends the whole diff through the full flow. One past PR looked like
   a pure checklist edit and also changed a file under `.github/workflows/`. Catalog output
   regenerated by proofread item 6 is the one exception.
2. None of those files carries behavioural risk. Markdown that instructs an agent or
   drives automation _is_ behaviour and takes the full flow: `**/SKILL.md`,
   `**/AGENTS.md`, `**/CLAUDE.md`, a repository review guide `docs/review.md`
   and its class catalogue `docs/review-classes.md`, command, hook and prompt
   files, and any `.github/**/*.md` a tool or a check reads. So does a runbook a human executes —
   deploy, migration, incident — where the hazard is a wrong step, which no proofread
   of wording catches. The lane is for prose a human reads.
   **Genuinely unsure → full flow.**

Inside the lane these substitutions are rules, not per-run judgment, because a full defect
review of prose-only PRs finds little beyond wording precision, while every extra push draws
another round of bot reviews:

- **§2** — use the proofread pass below instead of the full defect review.
  Run a repository-required closeout once when applicable, as item 8 describes.
  Record which review was skipped and which evidence was obtained.
- **§3** — skip external scans unless the user explicitly requested them or
  trusted repository policy requires them; then apply §3 for that scope.
- **§4** — unchanged. A repository's `.md` gate is usually path-scoped and cheap.

Name each skipped step and the lane as its reason, in the PR body and in the final report.

The proofread pass is one read of the full diff against base. Check 1–4 in the diff, then
do 5–8:

1. Claims about system behavior are checked against the code or config they describe —
   quantities, defaults, directions, bounds. Exact wording: inclusive or exclusive,
   faster or smaller.
2. Cross-references and paths resolve.
3. A command or flag the diff adds or changes is checked against the tool or script it
   invokes — run `--help`, read the script.
4. Each edit sits next to the rule it belongs with, not at the end of the file.
5. Grep the repo for every path, heading, and rule name the diff moved, renamed, or
   removed, and for the old wording of every current-state claim the diff changes
   (deployed or not, owner, date, location). Read each hit. A renamed doc leaves live
   links in files the diff never touched; a changed state leaves the old state asserted
   in README, checkpoint, and runbook files the diff never touched.
6. Regenerate the docs catalog when a doc was added, renamed, or removed
   (`pnpm docs:index --write`, or the repo's equivalent). Commit the generator's
   complete output — never hand-edit or partially stage it. Generators scan the
   worktree, not HEAD: when unrelated dirty tracked docs or untracked `.md` files
   would leak into the output, run the generator in a clean temporary worktree at
   the proposed head — with every intended edit, proofread fixes included, amended
   in first — and copy the whole artifact back. Pre-existing uncommitted
   edits to the catalog artifact itself cannot survive regeneration — that is a
   §1 stop.
7. Run the repo's context-budget checks when a `README`-class file changed.
8. Run the repository's required closeout review when applicable, resolving
   its exact command from the current repository instructions. Use a clean temporary worktree at the
   proposed head if unrelated edits would enter its input. Read the actual report;
   a successful process alone is not a clean verdict. Reuse a completed pass for
   the same state and scope. If the tool cannot run, state the exact limitation;
   do not replace a required pass with an undisclosed skip. A repository without
   this requirement does not acquire it from this example.

**One push.** The limit is on pushes, not commits. Until this run's first push, let the
proofread reshape the work freely — but amend only commits that have never been pushed;
on a branch that is already published, add a commit. §2's separate-commit rule does not
apply, because the lane skipped §2. Finish the proofread before that push; it is not a
pass you complete afterwards. Fixes still go out: a confirmed finding or a red required
check is fixed and pushed as §6 requires, whoever raised it — a human, a bot, CI, or you,
re-reading your own diff. Name any extra push in the report, with what the proofread
missed. Each push re-triggers every bot reviewer, and that noise buries the comments that
matter.

Everything else is unchanged — branch, scoped commit, gates, truthful PR body,
follow-through.
